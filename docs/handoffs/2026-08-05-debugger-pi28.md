## Findings

### Fixed (test-first, production seam)

1. **Routine interval clamp was `[2000, 300000]`; spec + PI-29 settings use `[60000, 604800000]`.** A routine configured with `scheduleMs: 86400000` (1 day) passed PI-29 validation but the scheduler silently clamped it to 300000 (5 min), firing ~288× too often. Fixed constants and clamp; added `120000`, `604800000`, `1e9`, `0`, `30000` cases to the cadence test.
2. **Tick interval was clamped to `[2000, 300000]`; ticket + spec require gcd clamped `[5000, 60000]` default 10000.** A single 300000 ms routine ticked every 300000 ms, so `at`-minute checks could skip a minute entirely. Fixed with `gcd` + `clampTickMs`; at-only routines still contribute 60000. Existing "two intervals" AC now verified with gcd tick.
3. **`at` + `scheduleMs` precedence deviated from spec q1.** Implementation fired "either condition" (recurring at). Spec: `at` pins the FIRST fire, subsequent fires are `intervalMs` apart from that anchor. Fixed `isDue`: before the first fire with `scheduleMs` present, only `at` drives; after the first fire, only the interval drives; at-only routines (no `scheduleMs`) keep `at` recurring. Added a regression proving the interval does not fire before the first `at` alignment (start 09:30, `at: [540]`, `scheduleMs: 3600000` → silent until next-day 09:00, then hourly).
4. **`scheduleMs: null` was treated as "has interval"** (`!== undefined`) and fired every default 10 s, inconsistent with PI-29 which rejects null. Fixed `hasInterval` to `typeof === "number"` in both `createInternal` and `isDue`; null + `at` is now at-only, null alone is a `missing schedule` config error. Added regression.
5. **INV-6: throwing injected `now()`/`setTimer()` crashed the host** via an uncaught exception in the timer callback. Wrapped `tick()` in a bounded try/catch that stops the scheduler (no crash loop); `settle()` now tolerates a throwing clock. Added two INV-6 regressions.
6. **A scheduler with only disabled/invalid routines still scheduled a recurring no-op timer.** Now no timer is scheduled unless at least one routine is fire-able (INV-18). Added regression.

### Rejected / not fixed (documented)

- **`dueNames` includes a running routine.** `tick()` reports a routine as due even when single-flight skips the fire. Defensible: the routine IS due; the display layer (PI-30+) can surface "in flight". Not a fire-correctness defect.
- **Never-resolving `onDue` promise permanently stalls that routine** (single-flight can never release). Matches spec's single-flight semantics; not a timer leak (no timer is held). Documented for PI-30 wiring.
- **DST wall-clock shifts.** `minuteOfDay` uses local-time `Date` semantics; a skipped/repeated local minute can shift one fire. The spec does not define DST behavior; the scheduler is a pure function of injected `now()`. Out of scope for PI-28.
- **Dynamic routine add/remove mid-run.** The scheduler is static over its input array; lifecycle wiring is PI-30/PI-32. Out of scope.
- **Weird `name` characters.** The scheduler accepts any non-empty string; terminal-safety/redaction of names is a display-layer concern (PI-30/INV-2).
- **Huge `at` arrays.** Deduped at construction, `includes` is O(n) per check; 1440 max valid entries × 10 000 ticks stays well under budget (measured 8.9 ms).
- **`dueAt` NaN edge.** If injected `now()` returns NaN the minute-key guard never matches and the routine would be considered due each tick; bounded (no throw/crash), and NaN clocks are outside any real contract.
